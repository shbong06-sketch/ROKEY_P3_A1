만들려는 것이 무엇인가

두 개임.

1. 작업 일지(DB) — 공정이 한 바퀴 돌 때 "몇 시에 무슨 단계가 시작됐고, 몇 초 걸렸고, 성공했는지 실패했는지" 를 적어 두는 파일 하나
2. 관제실 모니터(웹) — 그 일지를 브라우저에서 보기 좋게 보여주고, "시작" 버튼도 달린 화면

왜 필요한가

지금은 로봇이 "TRANSFER 중입니다", "도킹 중입니다" 라고 계속 알림을 보내는데, 그걸 받아서 적어 두는 곳이 없음. 터미널 화면에 흘러가고 사라짐. 그래서 "방금 그 사이클 몇 초 걸렸지?" 를 물으면 답할 수 없음.

팀 설계 문서에도 "작업 기록의 저장 위치와 형식" 이 아직 빈칸으로 남아 있음. 이 작업이 그 빈칸을 채우는 것임.

프로그램을 왜 두 개로 나누는가

- ROS 쪽 프로그램: 계속 귀를 열고 듣기만 함. 알림이 오면 일지에 적음
- 웹 쪽 프로그램: 누가 물어보면 답하기만 함. 일지를 읽어서 화면에 보여줌

이 두 일은 성격이 반대임. 한 프로그램에 둘 다 시키면 "듣는 중이라 답을 못 하고, 답하는 중이라 못 듣는" 상황이 생김. 그래서 둘로 나누고 일지 파일 하나를 같이 보게 함. 한쪽은 적기만, 한쪽은 읽기만 함.

웹의 "시작" 버튼은 어떻게 되는가 — 우체통 방식

웹은 ROS 를 전혀 모름. 그래서

1. 사람이 웹에서 "시작" 을 누름
2. 웹은 일지에 "시작해 달라" 한 줄을 적어 둠 (우체통에 편지 넣기)
3. ROS 쪽 프로그램이 0.5초마다 우체통을 확인함
4. 편지가 있으면 대신 /start_cycle 을 호출하고 결과를 같은 줄에 적음
5. 웹이 그 줄을 읽어 "수락됨" 또는 "이미 실행 중" 을 보여줌

덕분에 팀장님 쪽 코드를 새로 만들 필요가 전혀 없음.

2. 웹 고도화 기능 — 목록과 우선순위

먼저 전제 하나. 웹이 ROS 메시지를 직접 받는 표준 방법은 rosbridge_suite + roslibjs(WebSocket)임. 다만 우리 구조에서는 권하지 않음. 이유는 세 가지임.

- 웹이 토픽을 직접 받으면 이력이 남지 않음. 봉승현 팀장님 ML 과 백승주님 사이클 분석의 입력이 사라짐
- recorder_node 가 어차피 DB 에 쓰므로, 웹은 SSE(text/event-stream)로 서버에서 밀어주면 지연 차이가 체감되지 않음
- 고빈도 값(로봇 위치 10 Hz)은 live 테이블 1행을 UPDATE 로 유지하면 DB 비대 없이 SSE 로 밀 수 있음

그리고 판단 기준. 2026년 기준 관제 화면의 수준을 가르는 것은 프레임워크 유행이 아니라 다음 5개의 유무임: 서버 푸시 / 도면 위 오버레이 / 이벤트 타임라인 / 리플레이 / 데이터 내보내기. 아래 우선순위는 이 기준과 "팀원 담당 업무에 직접 연결되는지"로 매겼음.

블록 1 — response 질문에 대한 답 (가장 중요)

▎ "관제 웹은 팀장님 코드를 바꾸지 않아도 동작합니다. 확인해 보니 관제에 필요한 값이 이미 전부 발행되고 있었습니다. /cycle/status 에서 현재 단계(state), 사이클 결과(status, reason), 진행 중 명령(active_command_id)을 받고, /sim_task/command·/navigation/command·/inspection/command 와 각각의 /result 를 함께 구독하면 단계별 operation, 팔레트, 성공·실패, 실패 사유를 모두 기록할 수 있습니다. 단계별 소요시간은 command 발행 시각과 result 수신 시각의 차로 관제가 직접 재면 됩니다.

블록 4 — PR 본문의 timeout 항목 확인 요청

▎ "PR 본문에 '시간 초과가 진행 중인 Isaac 동작을 직접 취소하지 않는다' 고 적어 주셨는데, 제 이해가 맞는지 확인 부탁드립니다. Task Manager 가 TIMEOUT 으로 실패 처리한 뒤에도 Isaac 안에서는 그 동작이 계속 돌고, 늦게 도착한 result 가 토픽에 올라오고, Task Manager 는 그걸 NO_ACTIVE_COMMAND 나 MISMATCHED_RESULT 로 버리는 것으로 이해했습니다.
