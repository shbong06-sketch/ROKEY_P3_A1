# Navigation 파트 PT 슬라이드 구성 (텍스트 원고)

- 작성일: 2026-09-27
- 담당: 이원호 (Navigation · 정밀 도킹)
- 담당 구간: **랙 팔레트 파지 완료 시점 → 자율주행 → 턴테이블 앞 정밀 도킹 → Place 직전까지** (Place 모션 자체는 시뮬 실행기 담당, 도킹 정확도가 그 성공 조건임)
- 브랜치: `feature/Inspection-Place-nav2` (작업), `feature/lwh` (문서)
- 기준 장면·지도: `Collected_smartfarm_v014_room_core_cabbage.usd` / `maps/Collected_smartfarm_v014.yaml`

## 이 문서의 사용법

1. 이 문서는 **팀 PT 전체의 구성이 아니라, 튜터님이 지정한 '필수 슬라이드' 10개 항목을 Navigation 파트에 맞춰 한 묶음으로 만든 원고**임. 다른 팀원 파트도 같은 항목을 각자 한 묶음으로 만들면 전체 PT 가 됨.
2. 각 슬라이드는 아래 4칸으로 구성함. **`본문` 칸의 텍스트는 그대로 PPT 에 복사해 쓰도록 작성했음.**
   - `목적` — 이 슬라이드가 어떤 평가 항목·질문에 답하는지
   - `본문` — PPT 에 올릴 문장·표 (개조식)
   - `도해` — 그림으로 그릴 것의 지시서 (직접 그려야 하는 부분)
   - `근거` — 저장소 안의 출처 파일·로그. 질문 받으면 이 경로를 열면 됨
3. 목표는 발표 통과가 아니라 **팀원 전원이 프로젝트 종료 후에도 이 구간의 설계·개발 내용을 다시 읽고 이해할 수 있게 하는 것**임. 그래서 "왜 그 값인가 / 왜 그 방식인가" 를 수치·로그와 함께 남김.
4. 코드는 붙이지 않음. 로직은 **한국어 의사코드(수도코드)** 로만 적음 (튜터님 지시: 프로그래밍 언어에 의존하지 말 것).

## N-01 | 파트 표지 · 담당 범위와 책임 경계

**목적** — 내 구간의 시작·끝과, 다른 파트와의 책임 경계를 한 장으로 못 박음.

**본문**

- 파트명: **Navigation & Precise Docking**
- 담당 구간: `PICK_HARVEST` 성공 직후 → `NAVIGATION` → **정밀 도킹 완료** → `PLACE_INSPECT` 시작 조건 충족
- 산출물: ROS 2 패키지 `smart_farm_navigation` (독립 패키지). 팀 `standalone_app.py` 에는 76줄만 추가하고 기존 줄 삭제 0
- 책임 경계 3가지
  - **내 책임**: 카터가 **어디에, 어느 방향으로, 얼마나 정확히** 서는가
  - **시뮬 실행기 책임**: 서 있는 상태에서 팔·리프트가 **어떻게 집고 놓는가**
  - **경계 조건**: 도킹 정확도가 Place 성공 조건임 → 도킹 거리 `standoff_m` 은 팀 Place 수정과 **한 쌍**으로 관리
- 이 구간의 최종 성공 판정: `/feeder_dock/result = SUCCEEDED` **와** 카터 최종 world 좌표. 눈으로 본 판단은 판정에 쓰지 않음

**도해** — 가로 6칸 공정 띠. `PICK_HARVEST → NAVIGATION → PLACE_INSPECT → INSPECT → CULL → CONVEYOR_OUT`. 2번 칸(NAVIGATION)을 진하게, 3번 칸은 테두리만(성공 조건 제공). 4~6번은 흐리게.

**근거** — `docs/0번_단계통합_완료보고_및_수정내역_260926.md` §1, §5-1

## N-02 | 비즈니스 요구사항 — 현황·이슈

**목적** — 평가 1번 "문제 정의: 해결하려는 현실 문제와 디지털 트윈으로 검증해야 하는 이유" 에 대한 Navigation 관점 답.

**본문**

- 대상 현장: 실내 수직형 스마트팜. 랙 → 검사·후처리 라인 사이의 **팔레트 반송**이 사람 손에 남아 있는 공정임
- 현황 이슈 3가지
  1. **좁은 통로**: 랙 통로 폭이 차체보다 근소하게 넓은 수준이라(본 장면 기준 약 1.7 m 급) 제자리 회전이 불가. 사람은 가능하지만 AMR 은 경로 자체에 후진이 들어가야 함
  2. **적재물 보호**: 운반물이 엽채류 팔레트임. 급가감속·급회전 시 적재물이 밀리며, 30 mm 이상 밀리면 후속 Place 가 실패함(팀 안전 검사 기준)
  3. **반송 끝단의 정밀도**: 반송의 목적은 이동이 아니라 **다음 장비에 짐을 정확히 넘기는 것**임. 로봇팔 역기구학이 성립하는 위치에 차체가 서야 하며, 허용 오차가 cm·도 단위임
- 왜 자율주행(Nav2)만으로는 부족한가 — 본 프로젝트에서 확인한 사실
  - Nav2 도착 시 최종 방향 오차가 **7~33°** 로 남음. 원인: 추종기(RPP)가 후진 허용 상태에서 제자리 회전을 하지 못하고, 팔레트를 적재한 상태에서 AMCL 방향 추정이 흔들림
  - 즉 "지도 위 좌표에 도착" 과 "장비 면에 직각으로 정렬" 은 다른 문제임 → **지도를 쓰지 않고 센서로 대상 면에 맞추는 정밀 도킹 단계**가 필요
- 왜 디지털 트윈으로 검증하는가
  - 실물로는 **접촉·전복 위험이 있는 실패**(통로 접촉, 도킹 중 구조물 걸림)를 반복 재현할 수 없음. 본 구간은 그 실패를 의도적으로 225회 재현해 이득을 정했음
  - 차체 응답 지연·라이다 결손 같은 **하드웨어 특성**을 로그로 계측해 제어에 반영하는 절차를 시뮬레이션에서 확립할 수 있음

**도해** — 좌우 2단. 왼쪽 "사람이 하던 반송"(통로·팔레트·검사대 단면도), 오른쪽 "AMR 반송 시 추가로 필요한 것" 3개 아이콘(후진 경로 / 저가감속 / 면 정렬).

**근거**
- Nav2 도착 방향 오차 7~33°: `smart_farm_navigation/feeder_dock.py` 머리말, `docs/troubleshooting.md` §5
- 통로 회전 금지 근거(리그가 0.66 m 를 휩쓺): `config/stations.yaml` 하단 주석
- 팔레트 30 mm 밀림 기준: `docs/troubleshooting.md` §5-5

> **PPT 작성 시 주의** — 시장 규모·정책 자료 수치는 이 저장소에 근거가 없음. 팀 공통 슬라이드(스마트팜 시장/정책)에서 가져오고, 이 장에서는 **현장 이슈와 기술 요구**만 다루는 것을 권함. 없는 통계를 만들어 넣지 않음.

## N-04 | 로봇 모델링 — LiftRig 구성과 좌표계

**목적** — 필수 항목 ⑨. 우리 팀은 기성 로봇 하나를 쓰지 않고 **세 장비를 조립한 리그**를 만들었으므로 해당됨.

**본문**

- 로봇 이름: **LiftRig** = `Nova_Carter_ROS`(이동 플랫폼) + **리프트**(직동 관절) + **M0609**(6축 협동로봇) + **팔레트 포크**
- USD namespace 없음 → ROS 토픽이 루트에 붙음: `/cmd_vel`, `/chassis/odom`, `/tf`, `/front_3d_lidar/lidar_points`, `/clock`
- **앞뒤 정의 (이 프로젝트에서 가장 많이 혼동된 지점)**
  - `base_link` **+x = 카터의 앞 = 구동륜 쪽**
  - `base_link` **−x = 뒤 = 캐스터 · 리프트 · M0609 쪽**
  - 초기 배치 yaw **+90°** (앞이 월드 +y, 뒤가 통로 출구 쪽)
- 그 결과 **도킹은 후진 진입**이 됨. 팔이 리그 뒤쪽에 있어 앞으로 진입하면 팔이 대상 반대쪽을 향함. 이 배치는 팀의 랙 파지(P&P) 조건이므로 바꾸지 않음
- 좌표계 4개를 구분해서 씀

| 좌표계 | 정의 | 쓰이는 곳 |
|---|---|---|
| map = Isaac world | 지도 origin 이 world 기준이라 동일 | 작업점 좌표, 결과 보고 |
| `base_link` | 카터 섀시, +x 앞 | `/cmd_vel` 부호, 센서 변환 |
| `odom` | Isaac 시작 시 base_link 위치 | 멈춤 판정(상대 이동량) |
| 도킹 기준계 | **지도를 쓰지 않음.** 라이다가 검출한 대상 면의 직선 | 도킹 제어 전부 |

**도해** — 카터 측면도 1장에 화살표로 +x(구동륜, "앞")와 −x(리프트·M0609, "뒤")를 표기. 그 아래 평면도에 초기 yaw 90° 와 통로 출구 방향. **화면상 좌우와 로봇 기준 좌우를 섞지 말라**는 주의 문구를 넣음(초기에 부호를 반대로 잡아 엉뚱한 방향으로 간 사례 있음).

**근거** — `docs/ADR/ADR_basic.md` §4, `docs/troubleshooting.md` §4, `config/stations.yaml` 머리말

## N-05 | 로봇 모델링 — 치수·센서·물리 설정

**목적** — 평가 2번 "물리 속성이 올바르게 설정되어 있다", 그리고 왜 이 값이어야 하는지.

**본문**

| 항목 | 값 | 의미 / 이 값이어야 하는 이유 |
|---|---|---|
| 충돌 외형(costmap footprint) | x 0.14 ~ −0.607, y ±0.25 (패딩 0.03) | 리프트·팔까지 덮은 실측 외형. 뒤끝 −0.607 이 도킹 거리 하한을 결정함 |
| 최소 회전 반경 | 0.35 m | 경로 계획기(Hybrid-A*)에 넣는 값. 통로에서 곡선 후진이 가능한 한계 |
| 3D 라이다 | Hesai XT-32, `base_link` (−0.232, 0, 0.526) | 이 좌표를 도킹·점군 필터·연결 점검 **세 노드가 공유**함. 한 곳만 바꾸면 어긋남 |
| 라이다 발행 방식 | `fullScan = True`, 시뮬 10 Hz, 약 41,000점 | 끄면 렌더 프레임마다 60° 조각(약 6,900점)만 와서 AMCL 과 면 검출이 붕괴 |
| 2D 라이다 | 사용하지 않음 | 센서·채널은 있으나 메시지가 발행되지 않음(실측 4회 확인). 3D 점군 → `/scan` 변환만 사용 |
| 리프트 | 직동 관절 0 ~ 0.61 m. 0 m = 베이스 높이 0.796 m | 운반 자세 = 0.243 m (팀 `TRAVEL_BASE_HEIGHT` 1.0388 기준) |
| M0609 자세 | HOME 관절 [180,0,0,0,0,0], 파지 후 joint_1 +90° (→270°) | 운반 중 팔이 차체 폭 안에 들어오는 자세 |
| M0609 드라이브 | 강성 1e8 / 감쇠 1e4 / 최대힘 1e8 | **잡지 않으면 팔이 중력으로 처져 라이다에 잡히고**, 출발 직후 `collision ahead` 와 AMCL 0.5 m 오차가 발생 |

## N-08 | 기능 흐름 Flow Chart (전 구간)

**목적** — 필수 항목 ③. 명령 한 번이 들어왔을 때 끝까지 어떤 순서로 흐르는지.

**본문 — 순서 (숫자는 2026-09-26 실측 로그의 벽시계 소요)**

1. Task Manager → 시뮬 실행기: `PICK_HARVEST` → 랙에서 팔레트 파지, 결과에 `safe_to_navigate=true` (= 바퀴 브레이크 해제, 주행 허가)
2. Task Manager → `navigation_node`: `NAVIGATION`, `destination=FEEDER_DOCK`
3. `navigation_node`: 목적지 표에서 `approach=FEEDER_APPROACH` 확인 → Nav2 `NavigateToPose` 로 **world x −2.19, y −1.55, yaw 90°** 전송
4. Nav2: 통로를 **후진 경로로 탈출** → 접근 지점 도착 (약 36 s)
5. `navigation_node`: 실행 식별자(`command_id`)를 실어 `/feeder_dock/start` 발행
6. `feeder_dock`: Nav2 가 조용해지고 차체가 멈춘 것을 확인 → 면 검출 → 정렬 → 후진 → 직각 확인 → 미세 접근 → 완료 (약 58 s)
7. `feeder_dock` → `/feeder_dock/result` (같은 식별자) → `navigation_node` → `/navigation/result` `SUCCEEDED`, `reached_station=FEEDER_DOCK`
8. Task Manager → 시뮬 실행기: `PLACE_INSPECT` → **차체가 0.5초 이상 실제 정지한 것을 확인한 뒤** 팔 동작 → 벨트에 안착 (약 73 s)
9. 컨베이어가 팔레트를 비전룸 카메라 앞까지 반송해 정지 → **내 구간 종료**

- 실패 분기 3개
  - 4번 실패(경로 없음·시간 초과) → `NAV_FAILED`
  - 6번 실패 → `FACE_NOT_FOUND` / `STALLED_*` / `YAW_OFF_*` / `TIMEOUT` 중 하나로 **사유를 분리해** 반환
  - 8번 정지 확인 실패 → `BASE_NOT_SETTLED` (팔을 움직이지 않고 끝냄 → 안전)

**도해** — 위에서 아래로 흐르는 흐름도. 왼쪽 열에 주체(Task Manager / navigation_node / Nav2 / feeder_dock / 시뮬 실행기), 오른쪽에 단계. 실패 분기는 빨간 곁가지 3개로 뺌. 각 단계 옆에 실측 소요(36 s / 58 s / 73 s) 표기.

## N-09 | 세부 기능 ① `/scan` 생성 파이프라인

**목적** — 필수 항목 ⑥. Nav2 와 도킹이 쓰는 센서 입력을 어떻게 만들었는지. (평가 4번 "센서 데이터가 동작 결정에 반영된다" 의 근거)

**본문**

- 문제: 3D 라이다 점군을 그대로 쓸 수 없는 이유가 2개 있었음
  1. **자기 반사** — 리프트 기둥·팔·적재 팔레트가 라이다 옆에 있어 "발밑 장애물" 로 찍힘 → 출발 즉시 `collision ahead`
  2. **조각 발행** — 렌더가 느릴 때 한 프레임에 60° 조각만 오거나, `fullScan` 이어도 30~60° 섹터가 통째로 비어 옴 → `/scan` 의 한쪽 방향만 유효, AMCL 방향 흔들림, 면 미검출
- 처리 3단
  1. `cloud_self_filter`: `base_link` 기준 상자 안의 점 제거 → x [−0.65, 0.60], y [−0.60, 0.60], z [−0.20, 2.60]
  2. 같은 노드에서 **최근 0.25초(시뮬) 점군을 합쳐** 한 바퀴 스캔으로 만듦
  3. `pointcloud_to_laserscan`: 높이 −0.35 ~ 1.5 m 만 남김(바닥 제외, 대상 면 1.17 m 포함), `range_min` 0.3, 각 분해능 0.5° → `/scan`
- **가장 중요한 짝 조건**: 자기 반사 상자의 뒤쪽 경계 −0.65 m 는 **도킹 거리 0.92 m 보다 앞**이어야 함. 뒤로 넘기면 도킹해야 할 대상 면 자체가 지워짐. 차체 뒤끝이 −0.607 이므로 상자는 그것만 겨우 덮게 잡았고, 그래서 **도킹 거리는 0.75 m 아래로 두지 않음**
- 합침 시간의 상충: 길면 섹터 누락에 강하지만 이동 중 점이 번짐(0.3 m/s × 0.25 s = 7.5 cm). 0.25초는 그 타협점

**도해** — 좌→우 3박스 파이프라인(점군 → 필터+합침 → LaserScan). 박스 아래에 각 단계의 수치. 그림 아래에 **상자 경계 −0.65 와 도킹 거리 0.92 의 위치 관계**를 1차원 눈금자로 그림(이게 핵심이라 반드시 그림으로).

**근거** — `smart_farm_navigation/cloud_self_filter.py:30~45`, `launch/nav2.launch.py`, `docs/ADR/ADR_navigation2.md` §2.6

## N-10 | 세부 기능 ② Nav2 주행

**목적** — 필수 항목 ⑥ + 평가 3번 "파라미터 튜닝 근거를 설명할 수 있다".

**본문**

- 담당 범위: 랙 통로 안 → 통로 탈출 → 접근 지점(`FEEDER_APPROACH`) 도착까지
- 구성 선택과 근거

| 구성 요소 | 선택 | 왜 이것인가 (교체 이유 포함) |
|---|---|---|
| 전역 경로 계획기 | **Smac Hybrid-A\***, `REEDS_SHEPP`, `allow_reverse_expansion: true`, `minimum_turning_radius: 0.35` | 기본 NavFn 은 자세를 무시해 **통로 안에서 제자리 회전 경로**를 냄 → 랙 접촉. Reeds-Shepp 는 후진을 경로에 직접 넣음 |
| 지역 추종기 | **RPP**(Regulated Pure Pursuit), `allow_reversing: true`, `use_rotate_to_heading: false`, `desired_linear_vel: 0.3` | 후진 구간(cusp)을 그대로 따라감. 대신 **제자리 회전을 못 하므로 최종 방향은 도킹 단계가 맡음**(설계상 역할 분담) |
| 진행 판정 | **PoseProgressChecker** (`required_movement_angle` 0.3, 20 s) | 기본 판정기는 "회전" 을 진행으로 인정하지 않아, 느린 회전 중 15~20초마다 경로를 중단시켰음 |
| 도착 허용 | 0.25 m / 0.5 rad | 0.15 m 로는 도착점 0.16 m 앞에서 수렴하지 못하고 진동. 방향은 도킹이 보정하므로 느슨하게 |
| 회전 가속 한계 | `max_angular_accel: 20.0` | 2.0 이면 Isaac 쪽 가속 제한과 겹쳐 0.1 rad/s 로 기어감 → "**로봇이 2~3분 멈춰 있는 것처럼 보이는**" 현상의 원인이었음 |
| 위치 추정 | AMCL `alpha1~4` 0.1, `z_hit` 0.8, `z_rand` 0.2 | Isaac odom 이 정확하므로 주행 잡음은 낮추고 레이저 신뢰는 높임 |
| 부하·통로 | local costmap 4 m, inflation 0.45 | 0.70 으로 올리면 경고는 사라지지만 통로 복귀가 99초로 늘어남 |
| 속도 제한 | `velocity_smoother` 속도 [0.3, 0, 0.4], 가속 [0.3, 0, 0.6] | 적재물 밀림 방지. 속도 상한의 기준은 "팔레트·엽채류의 위치값이 유지되는 선" |
| 시간 기준 | 모든 노드 `use_sim_time: true` | 실시간 배율 0.3 → 벽시계로 판정하면 제한 시간이 3배 빨리 걸림 |

- 운용 규칙 1개: **Isaac 을 다시 실행하면 Nav2 도 다시 실행함.** 시뮬 시계가 0 으로 돌아가 TF·센서 시각이 어긋남

**도해** — 지도 이미지 위에 경로 1개(랙 → 통로 후진 → 접근 지점) + 접근 지점 좌표 말풍선. 오른쪽에 위 표에서 4줄만 추린 "바꾼 것과 그 이유" 요약.

**근거** — `config/nav2_params.yaml:149~199,314~334`, `docs/troubleshooting.md` §5

## N-11 | 세부 기능 ③ 정밀 도킹 상태기계

**목적** — 필수 항목 ⑥. 내 구간의 핵심 기능.

**본문**

- 설계 원칙 3개
  1. **지도를 쓰지 않음.** 라이다가 검출한 대상 면의 직선만 기준으로 삼음 (AMCL 오차·적재 시 방향 흔들림과 무관해짐)
  2. **상태기계(`DockLogic`)와 ROS 배선(`FeederDock`)을 분리함.** 상태기계는 ROS 없이도 돌아가므로 오프라인 모의와 실제 노드가 **같은 제어 논리**를 쓸 수밖에 없는 구조임
  3. 파라미터는 `DockParams` 한 곳에서만 선언하고, 노드가 그 필드를 그대로 ROS 파라미터로 노출함 (단일 출처)

| 단계 | 하는 일 | 다음 단계로 가는 조건 |
|---|---|---|
| `IDLE` | 대기. 현재 상태를 주기적으로 로그 | 시작 명령(`/feeder_dock/start`) 수신 |
| `SETTLE` | Nav2 감속 명령과 겹치지 않게 기다림 | Nav2 `/cmd_vel` 이 2.0 s 조용 **그리고** 각속도 < 0.03 rad/s, 선속도 < 0.02 m/s |
| `ALIGN_TO_GOAL` | 제자리 회전으로 **뒤쪽을 면 중심 방향으로** 돌림 | 남을 오차 < 4° 이고 실제 각속도 < 0.03. 회전이 안 먹혀도 오차 15° 안이면 후진으로 넘어감 |
| `REVERSE` | 도킹 선(면 중심을 지나는 법선)을 따라 후진 (0.10 m/s) | 목표점까지 0.06 m 이내 또는 면 거리 ≤ 0.94 m |
| `CHECK` | 도착 자세 검사 (**여기서는 회전하지 않음**) | 직각 ±3° 이고 좌우 ≤ 0.06 m → `CREEP`. 아니면 `BACKOFF` |
| `BACKOFF` | 면에서 0.90 m 더 물러남 | 물러남 완료 → `ALIGN_TO_GOAL` (최대 2회) |
| `CREEP` | 0.05 m/s 로 거리만 맞춤 | 면 거리 = 0.92 ± 0.03 m → `DONE` |
| `DONE` / `FAILED` | 결과 발행 (`run_id` 포함) | — |

- 실패 사유를 분리해 반환함: `FACE_NOT_FOUND`(면 8초 미검출), `STALLED_ALIGN/REVERSE/BACKOFF/CREEP`(3초간 이동·회전 없음), `YAW_OFF_±N도`(재시도 소진), `PHASE_TIMEOUT_<단계>`(45 s), `TIMEOUT`(전체 120 s, 시뮬 시계)
- **결과 오인 방지**: 결과 토픽은 래치(늦게 구독해도 마지막 값이 옴)라서, 시작 요청에 실행 식별자를 실어 보내고 **같은 식별자로 돌아온 결과만 인정**함

**도해** — 상태 전이도. `docs/architecture.md` §4 의 mermaid 를 그대로 그림으로. 전이 화살표에 조건 수치를 반드시 적음. `CHECK → BACKOFF → ALIGN` 루프는 굵게(재시도 구조가 이 설계의 핵심).

**근거** — `smart_farm_navigation/feeder_dock.py:160~350`, `docs/architecture.md` §4

## N-12 | 인터페이스 정의서

**목적** — 필수 항목 ⑥ 후반. 다른 파트와 맞춰야 하는 계약을 한 장에.

**본문 — 내 구간이 주고받는 인터페이스 전부**

| 이름 | 타입 | 방향 | 내용 |
|---|---|---|---|
| `/navigation/command` | `smart_farm_interfaces/TaskCommand` | Task Manager → `navigation_node` | `operation=NAVIGATION`, `destination=FEEDER_DOCK`, `command_id` |
| `/navigation/result` | `TaskResult` | `navigation_node` → Task Manager | `status`, `phase`(DRIVING/DOCKING/ARRIVED), `reason`, `reached_station` |
| `/navigation/status` | `ExecutorStatus` | `navigation_node` → 관찰자 | `state`(READY/BUSY/ERROR), `phase`, `detail` |
| `/feeder_dock/start` | `std_msgs/String` | `navigation_node` → `feeder_dock` | 실행 식별자(= `command_id`) |
| `/feeder_dock/result` | `std_msgs/String` (JSON, 래치) | `feeder_dock` → `navigation_node` | `run_id`, `status`, `reason`, `face_dist_m`, `yaw_err_deg`, `lat_m` |
| `/feeder_dock/status` | `std_msgs/String` (래치) | `feeder_dock` → 관찰자 | 현재 단계와 상세 |

| `/cmd_vel` | `geometry_msgs/Twist` | Nav2 · `feeder_dock` → Isaac | 속도 명령 (발행자 2개로 고정) |
| `/scan` | `sensor_msgs/LaserScan` | 내피 내부 | 도킹·AMCL·costmap 공용 |
| `/chassis/odom`, `/tf`, `/clock` | — | Isaac → 내피 | 위치·변환·시뮬 시계 |

- **혼동 주의(실측에서 실제로 틀렸던 것)**: `/sim_task/command` 는 `std_msgs/String` **JSON**, `/navigation/command` 는 **`TaskCommand` 메시지**임. 형식을 섞으면 노드가 아무 반응도 하지 않음
- 명령 전달 확인 규칙: `ros2 topic pub` 은 `--once --max-wait-time-secs 15` 로 보냄(구독자를 못 찾으면 무한 대기 대신 오류). **명령이 닿았는지는 노드 로그의 `command …` 줄로 판단**하고, 결과를 놓치지 않도록 **결과 구독 터미널을 명령보다 먼저 띄움**
- 한 번에 하나의 명령만 처리. 실행 중 같은 `command_id` 재전송은 무시하고, `BUSY` 는 최종 결과가 아니므로 캐시하지 않음

**도해** — 4주체(Task Manager / navigation_node / Nav2 / feeder_dock) 간 화살표 그림 + 위 표. 결과 JSON 예시 1줄을 그대로 넣음:
`{"run_id":"…CMD-002","status":"SUCCEEDED","reason":"NONE","face_dist_m":0.937,"yaw_err_deg":1.08,"lat_m":0.0}`

## N-13 | 알고리즘 ① 라이다 면 검출 (RANSAC)

**목적** — 필수 항목 ⑦. "지도 없이 대상에 맞춘다" 를 성립시키는 인식 부분.

**본문**

- 입력: `/scan` 한 장 (합쳐진 점군에서 만든 것). 출력: **면까지 거리 / 방향 오차 / 좌우 오차 / 면 중심 / 점 수 / 면 길이**
- 의사코드

```
1. 스캔의 각 측정값을 base_link 좌표의 점으로 바꾼다        (라이다가 x −0.232 에 있으므로 그만큼 옮긴다)
2. 로봇 뒤쪽 창 안의 점만 남긴다                            (x −3.4 ~ −0.5, y −1.3 ~ +1.3)
3. 점이 8개 미만이면 "미검출" 로 끝낸다
4. 가장 가까운 점을 찾고, 그 점에서 1.5 m 안의 점만 후보로 둔다   (다른 구조물 배제)
5. 후보에서 두 점을 무작위로 골라 직선을 세우기를 120번 반복한다
   5-1. 그 직선에서 3 cm 안에 있는 점을 내점으로 센다
   5-2. 내점이 8개 미만이면 버린다
   5-3. 직선의 법선이 로봇 뒤쪽 ±60° 밖을 향하면 버린다        (옆면 오검출 배제)
   5-4. 내점이 가장 많은 직선을 최선으로 남긴다
6. 최선 직선의 내점으로 중심과 방향을 다시 계산한다            (주성분 분석)
7. 면 길이가 0.6 ~ 1.6 m 밖이면 "미검출" 로 끝낸다              (대상 면 실측 1.15 m)
8. 거리 = 중심에서 법선 방향 거리, 방향 오차 = 법선의 각도,
   좌우 오차 = 중심의 좌우 성분  을 돌려준다
```

- 미검출 시 **왜 미검출인지 문장으로 남김**. 실제 로그 예: `line length 0.22 outside (0.6, 1.6)`, `no line: 27 pts, rejected {'short': 0, 'normal': 18}`. 이 덕분에 "센서가 안 보이는 것" 과 "조건이 안 맞는 것" 을 구분할 수 있음
- **검출 면과 USD 면의 구분**: 대상(TurnTable) 북단은 USD 기준 world y −3.60 이지만, 라이다가 실제로 검출하는 면은 **y −3.645** 임(실측 2건). 도킹 거리는 **검출 면 기준**임. 이 0.045 m 를 섞어 쓴 것이 과거 도킹 거리 오산(0.85)의 원인이었음

**도해** — 평면도: 로봇 뒤쪽에 검색 창(직사각형), 그 안의 점들, 맞춰진 직선, 법선, 목표점 G. ±60° 법선 허용 부채꼴과 길이 허용 구간(0.6~1.6 m)을 함께 표기.

**근거** — `smart_farm_navigation/feeder_dock.py:41~95`, `results/nav2_20260926_0133.txt:225~361`, `docs/ADR/ADR_navigation2.md` §2.2

## N-14 | 알고리즘 ② 굼뜬 차체 보상 (`settled_err`)

**목적** — 필수 항목 ⑦ + 챌린지(공학적 탐구). **이 파트에서 가장 설명할 값이 있는 부분.**

**본문**

- 관측된 사실 (실측 bag 계측)
  - 0.35 rad/s 를 명령해도 3초 걸려 0.26 rad/s 까지만 오름
  - 명령을 끊어도 각속도가 **초당 0.08 rad/s 씩만** 줄어듦 → 그동안 계속 돔
  - `/scan` 은 0.25초 합친 점군이라 방향 측정이 그만큼 **늦음**
  - 제자리 회전 효율은 실측마다 12~75% 로 편차가 큼
- 그래서 생긴 실패(24차 실측): **정렬 완료를 선언한 순간 차체가 아직 0.24 rad/s 로 돌고 있어 15° 를 더 돌았고**, 그 오차가 후진 중 증폭되어 도착 방향이 +20.7° 틀어졌음
- 해결: 제어에 쓰는 오차를 "지금 값" 이 아니라 **"지금 명령을 끊으면 멈췄을 때 남아 있을 값"** 으로 바꿈

```
남을 오차 = 측정한 오차
           − (각속도 × 측정 지연)        ← 측정이 늦은 만큼 이미 줄어든 분
           − (각속도² ÷ (2 × 감속률))    ← 명령을 끊어도 관성으로 더 돌 각도
```

- 쓰는 값: 측정 지연 0.5 s, 감속률 0.08 rad/s². 둘 다 **bag 에서 읽은 실측값**이며 차체가 바뀌면 다시 재야 함
- 함께 넣은 조건 2개
  - 정렬 종료 조건에 "실제 각속도 < 0.03 rad/s" 를 추가 (아직 돌고 있으면 끝났다고 하지 않음)
  - 도킹 시작 전 `SETTLE` 단계에서 Nav2 감속 명령이 끝나고 차체가 실제로 멈출 때까지 기다림
- 이 보정의 효과는 N-22 에서 정량 비교로 제시함 (좌우 오차 합격 206/225 → 225/225)

**도해** — 시간축 그래프 1개. (a) 명령 각속도 계단, (b) 실제 각속도(늦게 오르고 늦게 내림), (c) 방향 오차. "오차 0 을 선언한 시점" 과 "실제로 멈춘 시점" 사이에 남는 각도를 음영으로 표시하고 "이만큼을 미리 빼서 명령한다" 라고 씀.

**근거** — `smart_farm_navigation/feeder_dock.py:104~114`, `docs/troubleshooting.md` §5-5, bag `nav2_20260923_2154` 재생 표

## N-15 | 알고리즘 ③ 도킹 선 추종 후진 조향

**목적** — 필수 항목 ⑦. 실패를 고친 핵심 설계 변경.

**본문**

- 기존 방식(실패): **목표점 G 를 겨눔.** 남은 거리가 짧을 때 좌우 오차가 있으면 방향을 20° 이상 틀어 G 에 닿으려 하고, 응답이 느린 차체는 도착 전에 그 방향을 되돌리지 못함 → 반대쪽으로 +20.7° 초과
- 바꾼 방식: **면 중심을 지나는 법선(= 도킹 선)을 따라감.** "점" 이 아니라 "선" 을 따르므로 거리가 가까워져도 목표 방향이 튀지 않음
- 의사코드

```
1. 검출한 면에서 도킹 선(면 중심을 지나는 법선)을 세운다
2. 로봇이 그 선에서 옆으로 얼마나 벗어났는지(좌우 오차)를 구한다
3. 원하는 진행 방향 = 도킹 선 방향
                      + (좌우 오차를 0.6 m 앞에서 갚는 만큼의 기울임)
   단, 기울임은 최대 10° 로 묶는다        ← 굼뜬 차체가 되돌릴 수 있는 범위
4. 남은 거리가 0.4 m 안이면 좌우 오차 보정을 버리고 직각만 맞춘다
5. 조향 명령 = 1.5 × (N-14 의 '남을 오차')        상한 0.12 rad/s
6. 후진 속도 0.10 m/s. 목표까지 0.3 m 안에서는 비례해 줄인다
```

- 제자리 정렬은 목표점 G 가 아니라 **더 먼 면 중심 C** 를 겨눔. 같은 좌우 오차라도 각도가 작아, 그대로 후진하면 오차가 자연히 줄고 도착 방향도 덜 틀어짐
- 조향 상한을 0.20 → **0.12 rad/s** 로 내림: 0.20 을 5초 유지하다 정렬을 지나쳐 반대쪽으로 넘어간 사례가 있었음
- 멈춤(끼임) 감지: 명령을 내고 있는데 3초간 **이동 0.02 m 미만이고 회전 0.01 rad 미만**이면 즉시 중단. **회전도 이동으로 인정**하고, 단계가 바뀌면 기준점을 새로 잡음(회전 구간을 멈춤으로 오판해 후진 0.6초 만에 실패한 사례 때문)

**도해** — 평면도 2장 비교. 왼쪽 "점을 겨눔": 궤적이 도킹 선을 가로지르며 크게 휘고 도착 시 차체가 비뚤어짐. 오른쪽 "선을 따름": 궤적이 도킹 선에 부드럽게 수렴, 마지막 0.4 m 는 직각 유지. 두 그림에 실제 수치(21° vs 1.08°)를 적음.

**근거** — `smart_farm_navigation/feeder_dock.py:233~250`, `docs/troubleshooting.md` §5-3·§5-4·§5-5

## N-16 | 알고리즘 ④ 도착 판정과 재시도 정책

**목적** — 필수 항목 ⑦. 실패를 실패로 끝내지 않는 구조.

**본문**

- 도착 판정 3항목: **직각 ±3°**, **좌우 ±0.06 m**, **거리 0.92 ± 0.03 m**
- 왜 도킹 지점에서 회전하지 않는가: 팔이 든 팔레트가 차체 밖으로 나와 있어 **제자리 회전 시 구조물(컨베이어)에 걸림**. 자기 반사 제거 때문에 라이다로 미리 알 수도 없음(실측 22차에 실제 발생)
- 그래서 방향·좌우가 틀어지면 **회전 대신 물러남**: 면에서 0.90 m 더 물러나 다시 정렬 → 재진입. 최대 2회
- 물러나는 거리를 0.6 → 0.90 m 로 늘린 이유: **재시도 후진 거리가 곧 좌우 오차를 갚을 거리**임. 0.6 m 에서는 시도마다 오차가 15% 씩만 줄어 0.07 m 가 남았고, 0.90 m 에서는 모의 전 케이스가 0.06 m 안으로 들어옴
- 재시도를 다 쓰면 **직각만 맞추고 진행**함(좌우는 포기). 도킹 자체를 실패로 끝내는 것보다 팔 쪽 여유로 흡수하는 편이 낫다는 판단. 대신 결과 JSON 에 실제 좌우 오차를 그대로 실어 보내 다음 단계가 판단할 수 있게 함
- 비용: 재시도가 붙으면 도킹이 최대 시뮬 75초까지 늘어남 → `navigation_node` 의 도킹 제한 시간을 시뮬 시계 150 s 로 둠

**도해** — 도착 판정 3항목을 과녁 그림으로(방향 / 좌우 / 거리). 옆에 재시도 루프 그림: 도착 → 판정 실패 → 0.90 m 후퇴 → 재정렬 → 재진입, 최대 2회.

**근거** — `smart_farm_navigation/feeder_dock.py:118~150,305~330`, `docs/troubleshooting.md` §5-3·§5-5

## N-17 | 주요 모션 — 이 동작이 나오게 된 이유

**목적** — 필수 항목 ⑧. 튜터님 강조: **"어떻게 그 모션이 나오게 되었는지 잘 설명해야 함."**

**본문 — 이 구간에 눈으로 보이는 모션 5개, 각각 왜 그렇게 되었는가**

| 모션 | 눈에 보이는 것 | 왜 그 모션인가 (대안을 버린 이유) |
|---|---|---|
| ① 통로 **후진 탈출** | 카터가 통로 안에서 돌지 않고 뒤로 빠져나옴 | 리그가 제자리 회전 시 0.66 m 를 휩쓸어 랙·팔레트에 닿음. 스크립트로 후진시키는 방법 대신 **경로 계획기가 후진 경로를 직접 만들게** 함(Reeds-Shepp) → 장면이 바뀌어도 같은 방식이 성립 |
| ② 대상에 **뒤를 보이며 진입** | 카터가 돌아서 후진으로 다가감 | 팔(M0609)이 리그 **뒤쪽**에 있음. 앞으로 진입하면 팔이 대상 반대쪽을 향하고, 리프트 쪽으로 정면 진입하면 자체 충돌. 배치는 팀 랙 파지 조건이라 고정 |
| ③ 진입 전 **잠깐 멈춤** | 접근 지점 도착 후 2초쯤 정지 | `/cmd_vel` 발행자가 둘(Nav2·도킹)이라 겹치면 안 됨 + 차체가 실제로 멈춘 뒤 측정해야 방향이 맞음. `SETTLE` 단계로 명시적으로 기다림 |
| ④ 도킹 중 **살금살금 후진** (0.10 → 0.05 m/s) | 매우 느린 후진과 아주 작은 조향 | 각속도가 명령을 1~3초 늦게 따라오는 차체임. 빠르면 조향이 늘 뒤늦게 들어와 정렬을 지나침. 또 적재물이 30 mm 밀리면 Place 가 실패함 |
| ⑤ 틀어졌을 때 **물러나 다시** | 도착했다가 0.9 m 앞으로 나갔다 다시 후진 | 도킹 지점 제자리 회전은 팔레트가 구조물에 걸림(실측). 회전 대신 거리를 확보해 다시 정렬하는 것이 유일하게 안전한 복구 |

- **추가 모션 1개(팀 파일에 넣은 것)**: Place 직전, 팔이 움직이기 전에 **차체가 0.5초 이상 실제로 정지한 것을 확인**함. 미끄러지는 중에 짐을 내리지 않기 위함이며, 확인 실패 시 팔을 움직이지 않고 `BASE_NOT_SETTLED` 로 끝냄

**도해** — 5칸 스토리보드. 각 칸에 카터 평면도 자세와 화살표, 아래 한 줄로 "왜". 시연 영상의 해당 시각(타임코드)을 각 칸에 적어 두면 발표 때 영상과 바로 연결됨.

**근거** — `config/stations.yaml` 주석, `docs/troubleshooting.md` §5-3·§5-5, `docs/0번_단계통합_완료보고_및_수정내역_260926.md` §2-2

**화면 1. RViz2 운용 화면** (`rviz/nav2_smartfarm.rviz`)

**화면 2. 상태 판독 터미널** — 판정에 쓰는 3줄

| 줄 | 예시 | 읽는 법 |
|---|---|---|

## N-20 | 검증 체계 3단과 정량 결과

**목적** — 평가 5번 "성공률·소요 시간 등 사전 정의 기준으로 정량 측정".

**본문**

- 왜 3단인가: Isaac 실측은 기회가 제한적이고(시간·기기) 실패 재현이 어려움. 그래서 **싼 시험부터 걸러 올리는 체계**를 만들었음

|---|---|---|---|---|
| 1단 · 오프라인 격자 | `sim_test/dock_sim.py` (ROS 없이 상태기계만) | 시작 자세 45종 × 차체 특성 5종 = **225 케이스** | 약 2분 | 방향·거리·충돌 **225/225**, 좌우 **224/225** (1건 0.063 m, 허용 0.06) |
| 2단 · ROS 회귀 | `sim_test/dock_regression.py` (현장과 같은 실행 묶음 + 합성 로봇) | 실제 노드·Nav2·토픽까지 포함한 10 시나리오 | 20~30분 | **10/10 통과** |

- 2단 시나리오 10개: 정상 / 방향 +20° / 방향 −30° / 좌로 치우침 / 우로 치우침 / 접근 지점 0.4 m 뒤 / **제자리 회전이 거의 안 되는 차체** / 이상적 차체 / **후진 중 끼임** / **면이 안 보이는 위치**
  - 뒤 2개는 "실패해야 정답" 인 시나리오임. 끼임은 3초 내 `STALLED_REVERSE`, 면 미검출은 `FACE_NOT_FOUND` 로 끝나야 통과로 셈

- **모의와 실측을 섞지 않는 규칙**: 모의 결과는 항상 "모의" 로 표기. 실측 여부는 `results/`·`errored/`·bag 으로만 판단

## N-24 | 다음 구간 인계 지점

**목적** — 평가 5번 "시작부터 완료까지 전체 파이프라인이 끊김 없이 연결된다". 내 구간이 어디서 끝나고 무엇을 넘기는지.

**본문**

- 내 구간 종료 시점의 상태

| 항목 | 상태 |
|---|---|
| 팔레트 | 턴테이블 줄기 벨트 위 안착 |
| 카터 | 도킹 자세 유지·정지, 포크 인출 완료 |
| 컨베이어 | Place 중 정지 → 자동 재가동 → 팔레트를 비전룸 카메라 앞까지 반송해 정지 |
| 결과 | `/sim_task/result` 에 `PLACE_INSPECT / SUCCEEDED` |

- 실측 로그로 확인된 인계 좌표: 팔레트 정지 위치 **world x −0.496, y −6.728**, 벨트 윗면 **z 0.769 m**, 벨트 속도 0.30 m/s
- 인계 지점 2개
  1. **컨베이어 재가동 신호** — 검사가 끝났음을 알리는 호출(`inspection_done()`)을 누가 할지 정해야 함. 검사 미연결 구성에서는 10초 후 자동 배출로 두었음
  2. **Task Manager 명령 순서** — `INSPECT` → `CULL` → `CONVEYOR_OUT` 를 순서대로 발행 (불량 없으면 `CULL` 생략)
- 연결 방식 2안 (팀 결정 필요)
  - **A안**: 팀 올인원 스테이션이 검사→솎아내기→배출까지 시뮬 내부에서 자체 진행. 실행 인자 하나만 빼면 됨. 시연에 유리하나 Task Manager 통제 밖
  - **B안**: Task Manager 가 단계별로 지휘. 검사 노드가 명령을 받고 결과를 반환하는 구현이 필요
- 내 파트의 후속 역할: 배출 후 카터를 다른 지점으로 보낼 때 다시 호출됨. 현재 인식하는 목적지는 `FEEDER_DOCK`, `RACK_DOCK`, `CORRIDOR_EXIT` 3개. **랙 통로 안에서는 제자리 회전을 시키지 않는다**는 제약은 그대로 적용됨

**도해** — 공정 띠에서 내 구간 끝(3번 칸 종료)에 깃발을 세우고, 오른쪽으로 인계 항목 2개를 화살표로. A안/B안은 갈림길로 표기.

**근거** — `docs/0번_단계통합_완료보고_및_수정내역_260926.md` §5, `docs/02-interfaces.md` §3
